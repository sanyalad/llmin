# Ведение проекта на GitHub

## Принцип

GitHub должен хранить не только код, но и историю проверяемых решений: гипотезы, эксперименты, ADR, benchmark-результаты и причины отказа от идей.

## Типы задач

- **Experiment** — проверяемая гипотеза с baseline, метрикой и заранее заданным условием успеха.
- **Implementation** — изменение с определённым контрактом и Definition of Done.
- **Bug** — расхождение фактического и ожидаемого поведения.
- **ADR** — архитектурное решение с альтернативами и последствиями.
- **Benchmark** — изменение набора задач, измерений или отчётности.

## Ветки и pull requests

- `main` всегда должен содержать воспроизводимое состояние.
- Рабочие ветки именуются `codex/<краткая-тема>` или `<автор>/<краткая-тема>`.
- Изменения входят через небольшой PR с одной проверяемой целью.
- Архитектурное изменение сопровождается ADR.
- Изменение promotion/demotion thresholds сопровождается benchmark evidence.
- PR сначала создаётся как draft и становится ready после локальных проверок.

## Требования к PR

PR должен объяснять:

1. что изменено;
2. почему это нужно;
3. какой риск создаёт изменение;
4. как результат проверен;
5. какие метрики изменились;
6. нужен ли rollback или migration;
7. затрагивает ли изменение контракты знаний или verifier.

## Релизы

До появления стабильного API используются milestone-релизы:

- `0.1.0` — воспроизводимый baseline pipeline;
- `0.2.0` — первая offline-кристаллизация;
- `0.3.0` — compiled skill и routing без LLM;
- `0.4.0` — автоматический quarantine/demotion;
- `0.5.0` — финальный Stage 1 benchmark report.

## Что не следует автоматизировать на старте

- автоматическое слияние сгенерированных PR;
- автоматическое повышение knowledge status без benchmark;
- массовое создание issues из свободного LLM-ответа;
- релиз при отсутствии воспроизводимого отчёта;
- удаление неудачных экспериментов: они сохраняются как отрицательные результаты.
