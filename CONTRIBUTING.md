# Участие в разработке

Проект находится на исследовательской стадии. Любое изменение должно помогать проверить главную гипотезу: может ли система превращать проверенный опыт в более дешёвое воспроизводимое знание без потери качества.

## Перед началом работы

1. Свяжите изменение с issue или кратко опишите проверяемую гипотезу.
2. Для архитектурного решения добавьте ADR в `docs/adr/`.
3. Не расширяйте полномочия исполнителя без threat analysis и отрицательных тестов.
4. Не меняйте пороги жизненного цикла знаний без benchmark evidence.

## Критерии изменения

- минимальный и явно ограниченный scope;
- типизированные входы и выходы;
- безопасное поведение при ошибке;
- наблюдаемость и отсутствие секретов в traces;
- тесты в соответствии с риском;
- воспроизводимый способ проверки;
- обновлённая документация.

## Коммиты

Используйте короткое описание результата в повелительной форме. Не смешивайте рефакторинг, изменение поведения и обновление benchmark без необходимости.
